# 가상 건물 확장 설계 검토

검토일: 2026-09-07  
대상: [가상 건물 확장 설계](2026-09-07-virtual-building-expansion-design.md) 및 현재 프로젝트 구현  
상태: 설계 보완 필요. 확장 구현 및 확장 모델의 통합 검증 전.

## 검토 의견

가상 건물 생성기를 매개변수화하고 기존 14계통을 여러 동으로 확장하는 방향은 프로젝트와 맞는다. 평면과 설비 배치를 `PLAN`으로 통합하면 현재 중복된 구역 정의를 줄일 수 있고, 동 간 정전·계통 추적 시나리오도 기존 데모 흐름을 확장한다.

다만 **“워커·API·화면 변경 없이 동작”은 현재 코드 기준으로 보장할 수 없다.** 부속동의 층 단면 계산은 화면 보완이 필요하며, 일반 스위치 추가는 전원 API의 ATS 식별 방식과 충돌할 수 있다. 지하층 표고와 검증 카운트에도 현재 구현과 다른 전제가 있다.

원본 설계문서는 수정하지 않았다. 아래 수정 방향은 제안이며, 구현 완료를 의미하지 않는다.

## 1. 우선 보완할 사항

### 1.1 부속동 추가 시 층 단면 계산 오류 — 높음

현재 `MonitorPage.tsx`의 `storeyList`는 동 구분 없이 모든 층을 표고순으로 정렬한다. `storeyClip()`은 바로 위 항목의 표고를 선택한 층의 단면 상한으로 사용한다.

본동과 주차타워의 1층처럼 표고가 같은 층이 있으면 바닥 부근만 남는 단면이 만들어질 수 있다. 서로 다른 동의 층고가 다르면 다른 동의 층이 중간에 끼어 선택한 층을 잘못 자른다. 현재 XY 절단 범위도 전체 동을 포함한다.

**수정 방향:** 같은 동의 다음 층 또는 해당 층의 실제 높이를 기준으로 단면 상한을 계산한다. “이 층 단면”이 특정 동까지 한정해야 하는지도 정의한다. 이를 이번 단계에 포함하거나, 부속동 단면 기능의 제한을 명시해야 한다.

근거: `web/src/MonitorPage.tsx:66`, `web/src/MonitorPage.tsx:87`.

### 1.2 지하층 4m 변경과 좌표 유지 지시 충돌 — 높음

설계는 B2·B1 층고를 4m, 표고를 −8m·−4m로 지정하면서 이를 현행 코드로 설명한다. 실제 생성기는 층고 3.5m, B2 −7m·B1 −3.5m를 사용한다.

설비 기준 높이 `zb`, `z2`뿐 아니라 차량 램프의 높이·길이·개구부 계산에도 3.5m가 직접 들어 있다. `H`만 교체하면 바닥과 설비·램프가 어긋난다.

**수정 방향:** 다음 중 하나를 설계에 확정한다.

- 지하층은 기존 3.5m와 기존 표고를 유지한다.
- 4m로 변경하고 설비 Z 좌표·램프 높이·길이·참·개구부 계산까지 갱신한다. 이 경우 “지하 좌표 불변”은 XY 배치 유지라는 의미로 한정한다.

근거: `samples/gen/gen_mep.py:13–17`, `:125`, `:138–144`.

### 1.3 일반 스위치와 ATS 식별 충돌 — 중간, 구현 선택에 따른 위험

`high` 밀도는 벽 스위치를 추가하지만 IFC 클래스와 연결 규칙을 정하지 않았다. 현재 전원 API는 모든 `IfcSwitchingDevice`를 ATS로 취급한다. 정전 시 같은 클래스 전체에 `TRANSFERRED`와 `Source`를 기록하고, 현재 전원 원천도 같은 클래스의 임의 한 행에서 읽는다.

일반 스위치를 `IfcSwitchingDevice`로 생성하면 일반 스위치까지 ATS 상태가 된다.

**수정 방향:** 스위치의 클래스·상태·연결을 정의하고 ATS를 구분하는 조건을 마련한다. API 수정 범위를 늘리지 않으려면 이번 단계에서 스위치를 제외하는 선택도 가능하다.

근거: `api/src/main/java/com/bim/api/StatusService.java:138`, `:148`, `:161–163`.

### 1.4 후생동 말단에 필요한 상류 공급 정의 누락 — 중간

후생동은 동일한 `fit_zone()` 말단 세트를 사용하지만 동 간 연결표에는 공조·냉난방수·급탕·배수 경로가 없다. 현재 위생기구는 급수·급탕·배수에, VAV는 공조·제어에, FCU는 냉난방수·전기·제어에 연결된다.

**수정 방향:** 후생동 `ctx`에 필요한 원천을 나열하고, 본동 공급·후생동 자체 장비·말단 구성 축소 중 방식을 정한다. 요소에 연결이 하나 있다는 검사만으로는 필요한 계통 연결의 완전성을 확인할 수 없다.

근거: `samples/gen/gen_mep.py:350`, `:354`, `:359`; 원본 설계 §4 동 간 계통.

### 1.5 말단 격자에서 계단실·개구부 제외 필요 — 중간

설계의 실 사각형은 현재 계단실 영역 일부를 포함한다. ST1은 x=10.4~13.0, y=10.0~14.6이고 ST2는 x=33.0~35.6, y=0.3~4.9이므로, x=13~20.6의 코어만 피해서는 충분하지 않다.

단순 직사각형 격자로 배치하면 계단실 내부나 슬래브 개구부 위에 말단이 생성될 수 있다.

**수정 방향:** 실 경계 안쪽 여유 거리와 계단실·샤프트·개구부 제외 영역을 정의한다. 격자 시작점·순회 순서도 정해 경보 대상으로 지정한 감지기 인덱스가 밀도별로 존재하는지 확인한다.

근거: `samples/gen/gen_mep.py:15–20`, `:101–108`; 원본 설계 §3.

### 1.6 화재감지 추적 검증 방향 오류 — 중간

설계의 연결 규칙과 현재 코드는 `감지기 → 층 중계기 → FACP` 방향이다. 따라서 “감지기 상류가 FACP로 도달”이라는 검증은 연결 방향과 반대다. API의 `dir=up`은 들어오는 연결을, `dir=down`은 나가는 연결을 따라간다.

**수정 방향:** 기존 규약을 유지하고 검증을 “부속동 감지기에서 `dir=down`으로 추적하면 FACP에 도달”로 수정한다. 검증 문구에 맞추기 위해 기존 연결 방향을 뒤집지 않는다.

근거: `samples/gen/gen_mep.py:317`, `:345`; `api/src/main/java/com/bim/api/SystemController.java:40–45`.

### 1.7 생성 출력과 DB 카운트 기준 불일치 — 중간

현재 생성기의 카운트는 `IfcElement`와 `IfcDistributionSystem` 기준이다. 워커는 개구부를 요소 적재에서 제외하고, 수송용 일반 `IfcSystem`도 계통에 포함한다.

현재 생성기를 워커 컨테이너에서 실행해 확인한 결과:

| 항목 | 개수 | 의미 |
|---|---:|---|
| 전체 `IfcElement` | 508 | 개구부 포함 |
| `IfcOpeningElement` | 34 | 요소 DB 적재에서 제외 |
| 워커 추출 요소 | 474 | DB 비교 기준 |
| `IfcDistributionSystem` | 13 | 일반 수송 계통 제외 |
| 워커 추출 계통 | 14 | 일반 `IfcSystem` 포함 |
| 직접 공간 소속이 없는 요소 | 34 | 개구부 |
| 간접 소속까지 확인해도 소속이 없는 요소 | 0 | 호스트를 통한 소속 인정 |

**수정 방향:** 원시 IFC 개수와 DB 적재 대상 개수를 구분해서 출력한다. “모든 요소는 공간 또는 층에 소속” 검사는 `get_container()`를 통한 간접 소속을 인정한다고 명시한다. 직접 `ContainedInStructure`만 검사하면 정상 개구부를 실패로 처리한다.

근거: `samples/gen/gen_mep.py:62–66`, `:362`; `ifc-worker/worker/extract.py:45–56`, `:89–98`.

## 2. 구현 전 명확히 할 경계조건

| 항목 | 보완 방향 |
|---|---|
| `--floors` 범위 | 2F·3F 개구부를 유지한다면 우선 `N ≥ 3`으로 제한한다. 낮은 층수를 허용하려면 관련 설비와 개구부를 조건부 생성한다. |
| `top`과 RF | 최상 지상층 상단인 RF 바닥과 옥탑 상단을 별도 값으로 정의한다. RF가 포함된 목록의 마지막 `z+h`를 `top`으로 쓰면 기존 배기 덕트의 `RF-top+1.2`가 −1.8m가 될 수 있다. |
| 기본 부속동 검증 | 기본 `annex=1`에서는 P동만 검증한다. `W1F` 검증은 `annex=2` 실행에 둔다. |
| 목표 요소 수 | 약 3천·1만 5천은 측정 전 목표다. 개구부를 제외한 요소 수 기준인지 명시하고 실제 생성 후 확정한다. |
| IFC 커밋 | 현재 `.gitignore`는 `samples/*.ifc`를 제외한다. 기본 IFC를 커밋하려면 해당 파일만 예외로 둘지 결정한다. |

`top` 근거: `samples/gen/gen_mep.py:238`. 낮은 층수 근거: `samples/gen/gen_mep.py:263–265`.

## 3. 유지해도 좋은 설계 방향

- `PLAN`을 공간 생성과 설비 배치의 공통 입력으로 사용한다.
- 기존 계통 이름과 `Pset_BimStatus` 규약을 유지한다.
- `IfcSite` 아래 여러 `IfcBuilding`을 배치한다. 현재 워커의 공간 트리 추출은 해당 계층을 순회할 수 있다.
- 층 이름에 동 접두어를 붙여 현재 이름 기반 층 필터의 충돌을 피한다. 다만 이것만으로 단면 계산 문제는 해결되지 않는다.
- 기본 모델과 대형 모델을 분리하고, 대형 모델을 다음 단계의 타일링 비교 기준으로 사용한다.

공간 트리 근거: `ifc-worker/worker/extract.py:8–27`.

## 5. 검토 범위와 한계

설계문서를 생성기, 워커 추출 코드, 계통 추적·전원 API, 모니터링 화면, BMS 시뮬레이터와 대조했다. 기존 생성기를 워커 컨테이너에서 실행해 요소·계통 수와 공간 소속을 확인했다.

확장 모델은 아직 구현되지 않았으므로 확장 후 생성 성공, 업로드·변환·화면 동작, 성능 수치는 검증하지 않았다. 코드와 원본 설계문서의 변경 없이 이 검토 문서만 추가했다.
